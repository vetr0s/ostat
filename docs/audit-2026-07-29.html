ostat — project audit

29 July 2026vetr0s/ostat @ 6684378whole-project audit

ostat is in better shape than a two-day-old project has any right to be: the arena discipline is sound, the file-level comments are genuinely excellent, and the tests that exist are well-written. But it has one class of bug that will bite the first person who uses it, including you — the markdown preprocessing pass is line-oriented and has no concept of an inline code span. Writing a regex like [^a-z] inside backticks aborts the build with an error naming a “note” you never wrote. That is not hypothetical; I reproduced it against the built binary, along with seven other confirmed defects in the same family. Fix the code-span blindness first, because every other item on this list is a smaller problem than a generator that refuses to build ordinary technical prose.

Scope note

Every finding below marked reproduced was executed against build/debug/ostat with a purpose-built fixture, not inferred from reading. Findings marked by reading were confirmed in the source but not run. Two agent claims did not survive verification and have been dropped rather than softened: ~~~ mid-line is harmless (the fence check requires line-start), and the note counter does not desync between the HTML and feed passes.

What is solid

Worth stating plainly, because it is real and should not be disturbed by the work below.

The two-arena model (main.odin:37-50, 146-171) is the best structural decision in the project. perm for anything a ^Page points at, scratch for per-build intermediates, one arena_destroy at the end. There is not a single manual free in 2,779 lines and that is a direct consequence.

No slice can go out of range in the preprocessing pass. I had an agent check every slice expression in the four preprocessing files against its guard, individually — md_inline's <p> stripping, the table scanner's bounds, the note-definition parser, the delimiter-row parser, all four highlighter scanners. Every one is correctly guarded. Odin panics on a bad index, so this is the difference between a crash and none.

Multi-byte UTF-8 is safe in the highlighter despite byte indexing, because is_digit, is_ident_start and is_hex_letter all reject bytes ≥ 0x80, so no token ever starts or ends mid-codepoint. (The same cannot be said of truncate_words — see finding 5.)

Symlink loops are impossible. The directory iterator stats with SYMLINK_NOFOLLOW, so neither walk_content nor copy_tree can recurse into a cycle. No guard is needed and none should be added.

The Note_Style two-renderer design — one markdown source producing margin notes for HTML and numbered absolute-anchored endnotes for RSS — is a genuine idea, cleanly factored, and pinned by a regression test. The file-level doc comments across src/ are the strongest documentation in the repo; every one I spot-checked against the code was accurate. Builds are deterministic (both directory walks sort explicitly, with the reason written down) except for one clock read, which finding 21 turns into an asset.

Findings

1. The preprocessing pass cannot see inline code reproduced

This is one root cause with four distinct symptoms, and it is the whole reason this audit is worth acting on. apply_inline (markdown.odin:173-181) skips a line only when line.fence is set, and split_source_lines sets that flag only for ``` and ~~~ block fences. Backtick spans, four-space indented code blocks, raw HTML blocks and link destinations are all invisible to it.

1a. Ordinary prose aborts the build. notes.odin:147-152. Any [^…] outside a block fence is treated as a note reference; an unmatched one fails the build. Reproduced:

$ cat content/blog/regex.md
Match a non-letter with `[^a-z]+` in your pattern.

$ ostat build site
ostat: .../regex.md: note "a-z" is used but never defined
exit=1

Regexes, POSIX character classes, BibTeX keys and array indexing all contain [^. The error names a concept the author never used, so the first encounter is pure confusion. [^] can never resolve, because empty labels are rejected at definition time.

1b. ~~ inside a code span corrupts the code. gfm.odin:27-53. The preprocessor injects <del>, then cmark escapes it inside the span, so the reader sees the literal tags where they wrote tildes. Reproduced — source Use `a ~~ b ~~ c` literally. renders as:

<p>Use <code>a &lt;del&gt; b &lt;/del&gt; c</code> literally here.</p>

1c. ~~~ at line start silently swallows the rest of the document. markdown.odin:165-168. Fence tracking is a bool toggle that ignores fence length and fence character, so an unpaired ~~~ in prose turns everything after it into one code block. Exit 0, no warning. The same bug means a four-backtick block containing a three-backtick example — the standard way to document Markdown — terminates early.

1d. Indented fences and tables are de-nested out of lists. markdown.odin:116-119, 143-147. is_fence_marker trims leading space, so a fence inside a list item is recognised, open_html_block then forces a blank line that terminates the list, and the body is emitted at column 0 still carrying its indent.

Fix shape

All four need the same thing: the line scanner must track inline code spans and indented code blocks, not just block fences. That means a real inline scan in apply_inline — walk the line, toggle on unescaped backtick runs, and skip rewriting inside them — plus indentation tracking in split_source_lines. Roughly a day, and it retires 1a through 1d together.

2. Front-matter slug escapes the output directory reproduced

content.odin:158-165 takes fm.slug verbatim; render.odin:212-219 concatenates it into a path and calls make_directory_all. Nothing rejects /, .., spaces or empty components. With "slug": "../../escaped" ostat created a directory two levels above the output tree before failing the write with a confusing Not_Exist. A typo scatters directories outside public/; the content file is the least-trusted input in the system and it controls a write path.

3. Note labels reach HTML attributes unescaped reproduced

notes.odin:193-203. validate_note_label rejects only empty, whitespace and duplicate labels; ", < and & go straight into id= and for=. This is the only user-controlled string in the pass that skips html_escape. A label containing a quote produces visible garbage markup and a stray </label>, silently, exit 0. Author-controlled so not remote XSS, but it is a real escaping gap and the fix is one html_escape call plus a stricter validator.

4. A repeated note reference emits duplicate ids reproduced

notes.odin:153-167 counts references but nothing uniques the emitted markup. Referencing one note twice produces two elements with id="sn-dup" (confirmed: count of 2). Both labels resolve to the first checkbox, so on narrow screens tapping the second marker opens the first note. In feed mode you get two <sup id="fnref-N"> with the same N.

5. truncate_words emits invalid UTF-8 reproduced

text.odin:103-110. The backward scan for a space is byte-wise and safe when it finds one; the fallback cut = limit slices at an arbitrary byte offset. Any description over 160 bytes with no ASCII space — CJK, Thai, a long non-ASCII URL — is cut mid-codepoint. Confirmed with Japanese text: the <meta name="description"> contains a dangling 0xe3 and will not decode as UTF-8. Secondary: the 160 is a byte limit, so non-Latin descriptions are cut to about a third of the intended length.

7. p.section is retained but not cloned by reading

content.odin:105, 139. For nested sections, sub is a fmt.tprintf result on context.temp_allocator, and p.section = section stores it without cloning — while three lines later the same string is cloned for the map key. It is safe today only because nothing ever calls free_all(context.temp_allocator) and the scratch arena is never reset. The obvious future optimisation — resetting scratch per page — turns every nested page's breadcrumb into a use-after-free, and the test suite would stay green, because helpers_test.odin:6-12 points perm, scratch and temp at one allocator. This is the highest-value latent bug in the codebase.

Testing

51 tests, all passing in 1.3 ms, and the ones that exist are above-average: negative cases that assert mechanisms rather than output shape, regression tests that exist because something broke once, and a why comment on nearly every test. frontmatter.odin and gfm.odin are adequately covered and need nothing.

The problem is what is not covered: roughly 735 lines, 36% of non-test source, have no direct coverage, and it is precisely the I/O-adjacent half. render.odin (275 lines), main.odin (171), sitemap.odin (31) have none at all; content.odin (196) has one incidental test. Two structural things block it, both cheap to remove: 47 procedures carry @(private = "file"), and build-and-write are fused — render_page ends at write_output, so no layout can be asserted without touching the filesystem. Splitting each into build_x() -> string plus a write call is the single highest-leverage change available and unblocks about 480 lines.

A test that encodes the bug

markdown_test.odin:53 asserts that an undefined [^missing] fails the build. That is finding 1a written down as the specification, so fixing 1a requires changing this test. Its neighbour at markdown_test.odin:71, test_fenced_code_is_left_alone, reads as “code is protected” but only exercises block fences — giving false confidence about exactly the case that is broken.

Two further gaps worth naming. Draft and future filtering are dead code to every automated check: the demo site contains no draft and no future-dated page, so CI never enters those branches — and because w.today comes from time.now(), the demo build is clock-dependent, so a CI run before 2026-07-27 would have silently dropped a post while staying green. And there is no golden-output test, which is a shame, because this program is close to an ideal candidate: a pure function from content tree plus config to a deterministic file tree, with exactly one source of nondeterminism. Adding a -today override removes that, and makes future-date filtering testable for the first time.

Tooling

CI builds Odin from master on every run (ci.yml:20-23). That is slow — a from-source build against LLVM — and it means a red build is as likely to be an upstream commit as yours, which is the worst property for a repo that just went public and may receive its first outside PR. It also never verifies the toolchain README.md:160 pins. Either pin a release or add an odin version step so failures are attributable.

The only platform-specific code in the repo is never exercised. CI is Ubuntu-only, and on Linux the cmark discovery loop takes the empty branch — so the bash-3.2 empty-array guard written specifically for macOS is untested by anything but your laptop. A macOS matrix entry would cover the half of the docs that is currently unverified. Relatedly, CI installs Ubuntu's cmark 0.30.x while the README claims verification against 0.31.2: the “only four entry points, unchanged across that range” assertion is the load-bearing one and nothing tests it.

Minor: no odinfmt check despite a committed odinfmt.json and format_on_save in the Zed settings, so the formatter contract binds Zed users only. odin check runs without -vet -strict-style. And build.sh:63's exit "${PIPESTATUS[0]}" is unreachable — set -e fires first — so it is dead code that looks load-bearing.

Organisation, and the identity refactor

The module split is mostly coherent. Two exceptions worth acting on while you are in there. text.odin is two layers in one file: lines 25-151 are pure string utilities depending on nothing, lines 113-178 take ^Website and are layout concerns — and page_description reaches upward for DESCRIPTION_LIMIT, declared in render.odin:19, which makes the dependency direction unreadable. Separately, ^Website is threaded through five procedures of the highlighter purely to reach w.scratch; it needs an allocator, not the god-struct, and the cost is visible in gfm_test.odin:8-13 where a test fabricates a Website with two fields set just to call one function.

For the identity lift you asked for: about 70 site-specific values across four files, of which 14 are already in config.odin. The remaining ~56 are the actual work, in two dense clusters. render.odin:85-192 holds not just data but structure — write_home fixes three sections in a fixed order with fixed ids and the literal headings “Find Me”, “Elsewhere”, “Recent Posts”. html/head.html holds eight asset paths reachable only through a #load. Two stragglers are easy to miss: site_brand in text.odin:161-169 encodes the “split the title at the first dot” rule — vetr0s.dev-shaped logic that renders Dr. Foo as Dr<span class="accent">. Foo — and the root feed path "/index.xml" is hardcoded in three separate files.

Recommended order of work

Ordered so that each step makes the next safer, and so the demo-site replacement lands after the tests that would catch a regression in it.

  • Teach the preprocessor about inline code and indentation (finding 1). One fix, four symptoms, and it is the only item that makes ostat unusable for technical writing. Change markdown_test.odin:53, which currently asserts the bug.
  • Validate and escape the untrusted strings (findings 2, 3): reject /, .., whitespace and empties in slug and in note labels, and html_escape the label. Small, and it closes the two paths where content controls output structure.
  • Split build-string from write-to-disk in render_page, render_sitemap and write_feed, and drop @(private="file") where it only blocks tests. Unblocks ~480 lines and is a precondition for the next two items.
  • Add a -today override and a golden-output fixture site containing a draft, a future post, a slug override, a nested section, and a code span with [^ and ~~ in it. Covers the untested 36% in one shot, and makes the build deterministic.
  • Replace the demo site with the dogfooded docs. Do it now, on top of a golden test, so the swap is verified rather than hoped at. Retire the personal photos, the resume.pdf config entry and the gh fetch in dev, and replace CI's hardcoded kitchen-sink assertion with a sitemap-to-disk invariant that survives content changes.
  • Lift site identity into one place, including write_home's structure, head.html's asset paths and site_brand. Correct the claim at config.odin:6-8 to what actually holds.
  • Fix the latent allocator bug (finding 7) by cloning p.section into perm, and give helpers_test.odin two real arenas so the class stays visible.
  • Tooling pass: pin Odin in CI, add a macOS matrix entry, add an odinfmt check, document python3, and clear the README and colophon drift in the table above.
